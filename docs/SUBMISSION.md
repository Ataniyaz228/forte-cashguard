# CashGuard — сервис проверки кассовой дисциплины по видео

Черновик комплекта сдачи по разделу 8 ТЗ. Адреса, ключ и итоговые метрики заполняются перед сдачей.

## 1. Адреса и доступ

| Что | Значение |
|---|---|
| Веб-интерфейс | https://4rie6ay34pajzk-8000.proxy.runpod.net |
| API | https://4rie6ay34pajzk-8000.proxy.runpod.net/api/v1/analyze, …/api/v1/jobs/{job_id} |
| API-ключ жюри | передаётся отдельно, заголовок `X-API-Key` |

```bash
curl -X POST https://4rie6ay34pajzk-8000.proxy.runpod.net/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video.mov"
# {"job_id":"…","status":"processing"}
curl https://4rie6ay34pajzk-8000.proxy.runpod.net/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
```

Ответ `done` содержит обязательные поля `job_id`, `status`, `verdict`, `violations`. Каждое событие имеет `type`, `timecode_sec`, `description`, `evidence_frames` (1–3 JPEG в base64 с `timestamp_sec`). Дополнительные поля события: `type_code`, `confidence`, `rule` (документ, пункт, текст, ссылка). Строгий парсер может их игнорировать. Нормативная ссылка продублирована в `description`.

## 2. Запуск и использование

```bash
uv sync                                   # Python 3.12, зависимости из uv.lock
echo "CASHGUARD_API_KEYS=<ключ>" >> .env  # ключ не хранится в git
.venv/bin/python -m datathon.cashguard serve --port 8000
.venv/bin/python -m datathon.cashguard analyze video.mov --no-images   # локальная проверка
```

Веса моделей скачиваются один раз в кеш Hugging Face. После этого обработка работает без интернета (`HF_HUB_OFFLINE=1`). Пользователь открывает веб-страницу, загружает `.mov`, видит статус, вердикт и карточки событий. В каждой карточке тип, таймкод (по клику видео перематывается), описание, основание и кадры. Авторизация, история и экспорт не требуются (FAQ 27). API жюри защищено ключом.

## 3. Архитектура и подход

```
.mov → декодирование по реальным PTS
     ├─ 3 кадра/с → RT-DETR (люди) → временная линия: сколько людей, вход/выход, отсев
     │                               отражений за стеклом, сидит/стоит → уход с рабочего места
     └─ 0,5 кадра/с → Qwen3-VL-8B на автоматически увеличенной зоне действия: вопросы «да/нет»,
                      ответ — P(yes) из логитов (сейф открыт, наличные/сумка/документы, еда…)
→ точечные проверки в нужные моменты: модель сама находит сейф, замок, стол, ноутбук и дверь
  (grounding) и отвечает по увеличенным фрагментам (стол — 4 фрагмента, экран ноутбука)
→ эталон — само видео: участок двери сравнивается с его видом в начале записи
→ временные правила (rules.py) → события: таймкод, уверенность, уровень
  («подтверждено» / «требует проверки»), окно уязвимости (сколько секунд и сколько людей)
→ отчёт: тип, норма (дословно), описание из измеренных фактов, 1–3 кадра с рамками,
  «до/после» — тот же участок в начале записи и в момент нарушения, изменения подсвечены
```

- **Оригинальная идея: каждое видео — сам себе эталон.** Мы не учим модель, как выглядит нарушение. Мы измеряем, насколько и как долго помещение отклонилось от своего же безопасного состояния в начале записи. Модель не дообучается, эталон берётся из той же камеры; условие — участок виден в начале записи. Пороги правил при этом подобраны на 40 обучающих видео. Так ловится незакрытая дверь (E032), так строится доказательство «до/после» и окно уязвимости в секундах.
- **Почему не одна обученная модель.** 40 уникальных роликов, по 1–2 примера на тип, тест под другим углом. Сквозное обучение здесь переобучится. Детектор и VLM работают без дообучения под конкретную камеру, а логика нарушений записана явно и проверяется.
- **Почему описания по шаблону.** Критерий 4 штрафует неподтверждённые утверждения. Текст собирается только из измеренных фактов (время ухода, что осталось на столе) и дословной нормы. Свободная генерация не используется.
- **Таймкод.** Как в разметке организаторов: момент, когда нарушение становится видно (кассир встаёт и уходит, входит следующий посетитель). Для нарушения по бездействию — момент, где обязательное действие должно было произойти.
- **Расширяемость.** Новый тип = новый вопрос к VLM + правило + запись в `norms.py`. Переобучение не нужно.

## 4. Модели и лицензии

| Компонент | Модель | Лицензия |
|---|---|---|
| Детектор объектов | `PekingU/rtdetr_r50vd_coco_o365` (RT-DETR) | Apache-2.0 |
| Визуально-языковая модель | `Qwen/Qwen3-VL-8B-Instruct` (основной сервер, NVIDIA A40); `Qwen/Qwen3-VL-2B-Instruct` (резерв на ноутбуке) | Apache-2.0 |
| Фреймворки | PyTorch (BSD-3), Transformers (Apache-2.0), PyAV (BSD-3), FastAPI (MIT) | — |

Все модели выполняются внутри сервиса на нашей машине. Облачные AI-API не используются. Звук не анализируется, лица не распознаются и не идентифицируются.

## 5. Нормативные источники и сопоставление

Тексты проверены 17.10.2026 по ИПС «Әділет» (№ 231, № 14, № 48) и zakon.uchet.kz (№ 53 — adilet отдавал ошибку 500):

- Постановление Правления НБРК от 29.11.2019 № 231 — Правила кассовых операций и инкассации: п. 12, п. 19 подп. 2, п. 20, п. 22, п. 24, п. 75, п. 80.
- Постановление Правления НБРК от 24.02.2020 № 14 — Правила охраны и устройства помещений: п. 8, п. 16 подп. 1.
- Постановление Правления АРРФР от 03.04.2026 № 53 (рег. № 38336) — Требования к обеспечению ИБ банков: п. 71 подп. 9 (блокировка рабочей станции). Заменило постановление НБРК № 48 (2018), утратившее силу; на № 48 не ссылаемся.
- Правила «по отсутствию действия» (нет проверки удостоверения, нет пересчёта) срабатывают, если действие не видно: на очень плохом качестве видео они могут дать ложную тревогу (E030).
- Вопрос о сумке инкассации в периодических проверках упоминает её цвет (зелёная, как в обучающих видео); подтверждение по соседним кадрам — без цвета.
- Где норма регулирует событие косвенно (дверь, еда, посторонний в помещении, не являющемся сейфовой комнатой), это прямо сказано в описании события.

Принцип: правило срабатывает только по видимому действию или состоянию. Норма приводится как основание для проверки, а не как установленный факт нарушения. Невидимое (проводки, учёт, подлинность банкнот) сервис не утверждает.

## 6. Поддерживаемые типы событий

| Тип (поле `type`) | Как обнаруживается | Основание |
|---|---|---|
| Сейф оставлен открытым | VLM: дверца сейфа открыта (подтверждается по фрагменту сейфа), кассир сидит за столом до конца ролика или ≥15 с; либо уходит из помещения | № 231 п. 20 |
| Ключ оставлен в замке сейфа | после ухода кассира — вопрос по увеличенному фрагменту замка, найденному VLM | № 231 п. 80, п. 20 |
| Ценности оставлены без присмотра | после ухода кассира на столе что-то осталось (вопрос по пустой комнате); уточнение: наличные, сумка | № 231 п. 20 |
| Компьютер не заблокирован при уходе | после ухода модель смотрит на увеличенный экран найденного ноутбука: открыта программа или экран блокировки / выключен (E022); доля светлых пикселей — только если ноутбук не найден | АРРФР № 53, п. 71 подп. 9 |
| Наличные на столе при следующем посетителе | кассир одна, входит посетитель, а на столе лежат наличные | № 231 п. 20 |
| Сумка инкассации принята без проверки | появляется инкассаторская сумка при двух людях в комнате, удостоверение за визит не показано | № 231 п. 24 |
| Вложения сумки не пересчитаны | сумка вскрыта, работа с наличными (пересчёт или деньги на столе) < 10 с перед закладкой в сейф | № 231 п. 41, п. 24 |
| Посторонний в кассовом помещении | вошедший человек не садится, а стоит рядом с кассиром ≥5 с (клиенты садятся, инкассатор приходит с сумкой) | № 14 п. 8; № 231 п. 75 (если это сейфовая комната) |
| Еда или напитки на рабочем месте | VLM + подтверждение детектором (чашка/бутылка) или, если детектор не видит мелкий предмет, устойчивой серией кадров и увеличенным фрагментом стола | № 231 п. 12 |
| Личные вещи на рабочем месте | VLM + подтверждение детектором (сумка/рюкзак), исключая инкассаторскую сумку | № 231 п. 12 |
| Дверь кассового помещения не закрыта (уровень «требует проверки») | эталон — само помещение в начале записи: участок двери (найден моделью) сравнивается с его видом в начале; если вся вторая половина записи отличается — дверь осталась открытой (E032) | № 14 п. 8, п. 16 (косвенно, см. описание) |

Каждое событие помечено полем `level`: `confirmed` — подтверждённый сигнал, `review` — более слабый сигнал, который выдаётся, чтобы не пропустить нарушение (в кейсе пропуск хуже ложной тревоги). Вердикт `violation` ставится при любом событии. `CASHGUARD_REVIEW=0` оставляет только подтверждённые.

## 7. Ограничения и известные ошибки

- Не распознаются (обучающие видео, модель 8B):
  - пересчёт после ухода клиента (Х-34): счётная машинка выглядит работающей на всех кадрах этого ракурса; клиент выходит за 1,7 с до конца записи (E031);
  - приём денег до проверки удостоверения (X-2): модель отвечает «удостоверение» и «наличные» на один и тот же предмет в руке, как и на нормальном Х-3; как слабый сигнал правило дало 5 ложных тревог на искажённых копиях нормального Х-39, поэтому выключено (E018, E031);
  - дверь находится сравнением с началом записи (E032); если камера не видит дверь в начале (в проверке — приближение, обрезающее дверь), правило молчит;
  - X-1: по видео тип не установлен (возможна выдача неполной суммы — по кадру не проверяется);
  - Х-44: по нашей гипотезе — сомнительная банкнота не отложена; такой тип не распознаётся. Раньше ролик «находился» через ошибку модели (сумка инкассации на одном кадре), эта же ошибка давала ложную тревогу на Х-43 с перспективой; после проверки сумки по соседним кадрам (E027) оба случая честно молчат.
- Таймкод: медиана ошибки 1,2 с, максимум 3,0 с. Маленькая пачка на краю стола (Х-38) находится проверкой стола четырьмя увеличенными фрагментами (E026).
- Признак «ключ в замке» опирается на увеличенный фрагмент замка; на сильно ином ракурсе замок может быть не виден.
- Типы, связанные с уходом кассира (ценности, сейф, ключ, экран), есть только в одном ракурсе обучающих данных; устойчивость проверена на 120 синтетических искажениях, см. E026–E030.
- Где норма регулирует событие косвенно (дверь, еда, посторонний в помещении, не являющемся сейфовой комнатой), это прямо сказано в описании.
- Смартфон в кассе не сообщается: клиенты в нормальных роликах держат телефоны.
- Лица не распознаются, звук не используется; проводки, сверка, подлинность банкнот не оцениваются.
