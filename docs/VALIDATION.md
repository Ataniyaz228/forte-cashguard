# Данные, качество и доказательства

## До модели

Определите строку: клиент, транзакция, клиент-месяц, документ или другой объект. Уточните момент решения и горизонт целевой переменной. Проверьте диапазон дат, пропуски, дубли и ключи связей. При join сравните число строк до/после: неожиданный many-to-many может незаметно изменить задачу.

`datathon audit` делает описательный аудит всей таблицы. Не используйте корреляции с будущим holdout для отбора признаков. Анализ связи с target, создание гипотез и сегментов проводите на train/development.

## Как выбрать разбиение

| Использование | Разбиение | Ловушка |
|---|---|---|
| Предсказание будущих событий | time | Случайное разбиение может показывать будущее модели |
| Обобщение на новых клиентов/организации | group | Один клиент по обе стороны делает проверку слишком лёгкой |
| Независимые объекты без времени и общих сущностей | random, со stratify для классов | Сначала убедиться в независимости |

Каркас создаёт train/validation/holdout. Early stopping и выбор бинарного порога используют validation; итоговая таблица качества использует holdout. Для time одинаковые timestamps остаются вместе, а `gap_periods` исключает несколько уникальных дат около границ. Это не автоматический purge перекрывающихся окон таргета: горизонт, агрегации и необходимые интервалы нужно задать по кейсу.

GroupShuffleSplit делит группы, поэтому доли строк приблизительны. Временные доли считаются по уникальным timestamps. Совмещённый запрет пересечения клиентов и времени требует отдельного splitter: готовый каркас его не реализует.

Ни один splitter не распознаёт будущие признаки автоматически. Время статуса, погашения, решения оператора и агрегаты по всей истории часто содержат ответ. ID и target исключаются; allowlist должен проверить человек. Дубли событий между клиентами/разными IDs тоже требуют отдельного поиска.

## Метрика

Для классификации сохраняются accuracy, balanced accuracy, macro F1, log loss; для binary ещё ROC AUC, average precision, precision, recall и F1. Average precision — самостоятельная метрика, не точное синонимичное название площади под любой интерполяцией PR-кривой. При редком позитивном классе простая accuracy может быть высокой у бесполезного решения; ориентир — метрика организаторов и условия применения.

Положительный класс задаётся явно через `positive_label`. Для регрессии выводятся MAE, RMSE и R²; полезно добавить доменную метрику из brief. DummyClassifier использует частоты train; DummyRegressor — среднее train. Это только нижняя точка сравнения, а не замена разумному бизнес-правилу.

Если заданы стоимости ошибок, порог выбирается по минимальной сумме `FP × цена_FP + FN × цена_FN` на validation. Это сценарная оценка при заданных ценах, не доказанный денежный эффект. Для лимита проверок добавьте precision/recall@K и сравнение при одинаковом K. Порог нельзя оптимизировать на test/submission labels.

## Что показать в защите

Метрика, единицы, размер выборки, диапазон дат, правило разбиения, baseline и результат на одинаковых данных. При выводах по сегментам — размер каждого сегмента и поддержка гипотезы. Одна удачная выборка не доказывает устойчивость.

Если время и данные позволяют, проведите несколько development-folds, а финальный holdout оставьте нетронутым до выбора кандидата. Для оценки неопределённости используйте bootstrap с единицей ресемплинга по клиентам/группам или временным блокам; обычный bootstrap строк для зависимых событий может быть слишком оптимистичен.

Важность CatBoost не доказывает причину и не гарантирует стабильность. Для важного решения проверьте ablation на development-выборке, ошибки по сегментам и доступность признака в момент решения. Причинное влияние действий банка нельзя вывести из корреляции без дополнительных допущений или эксперимента.

## Для больших или иных данных

Для первого просмотра большого CSV: `duckdb.sql("SELECT * FROM read_csv_auto('data/raw/file.csv') LIMIT 10").df()`; затем агрегаты в SQL и чтение выбранных столбцов. Сначала проверьте автоматически определённые типы. pandas-аудит и готовое обучение используют RAM; при ~15 ГБ общей памяти оставьте запас системе.

Для текста: разделение по документам/авторам/времени, простой поиск или TF-IDF benchmark, ручная разметка небольшого development-набора и оценка релевантности/галлюцинаций по рубрике кейса. Для временного ряда: последний период отдельно, наивный сезонный прогноз, rolling backtest. Для аналитики без target: проверка знаменателя, устойчивость к очистке/сегментам, воспроизводимый SQL, честное различие наблюдения и причины. Готовая модель CatBoost не заменяет эти постановки.
