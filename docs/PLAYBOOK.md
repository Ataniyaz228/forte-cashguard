# План 24 часов

Время ниже — рабочий план команды, привязанный к старту 17 октября в 12:00. Официальный дедлайн — 18 октября в 12:00. Если правила объявят другие промежуточные сроки, обновите план сразу. Строгого разделения ролей нет: у каждого параллельного изменения просто должен быть понятный автор и проверяющий.

| Время | Результат этапа | Условие перехода |
|---|---|---|
| Сб 12:00–13:00 | Заполненная карта требований, цель и схема проверки | Понятны единица наблюдения, таргет/результат, формат сдачи и ограничения |
| 13:00–15:00 | Аудит данных, простой benchmark, первая метрика | Разбиение отражает использование; baseline воспроизводится одной командой |
| 15:00–18:00 | Одно выбранное направление и первый полный сценарий | Есть измеримое улучшение или полезная находка; выбор объясним |
| 18:00–21:00 | Сравнение вариантов и анализ ошибок | Каждое усложнение даёт пользу; неудачные варианты зафиксированы |
| 21:00–00:00 | Кандидат на сдачу и черновик защиты | Все обязательные пункты уже имеют доказательство; зависимости зафиксированы |
| Вс 00:00–06:00 | Проверка устойчивости, перерывы и отдых по очереди | Рабочая версия сохранена; никто не принимает критическое решение в одиночку в сильной усталости |
| 06:00–09:00 | Финальные графики, один показательный пример, ограничения | Цифры сходятся с логами; понятны сегменты, провалы и цена ошибок |
| 09:00–10:00 | Заморозка функций и фиксация параметров | Нет новых возможностей без обязательного требования из brief |
| 10:00–11:00 | Прогон как у жюри и резерв | Запуск из чистого терминала, файл сдачи, слайды, видео, README |
| 11:00–11:30 | Репетиция и проверка комплекта | Питч укладывается; можно ответить на вопросы о данных и метрике |
| 11:30–12:00 | Отправка и запас на ошибки | Есть подтверждение приёма и копия отправленных файлов |

## Когда менять направление

Если к 15:00 данные или цель всё ещё непонятны — уточнение у ментора полезнее ещё одного фреймворка. Если к 18:00 нет полного сценария — сократите объём до одного обязательного пути. Если к 21:00 прирост не повторяется — вернитесь к более простой версии и объясните, что проверили.

Проверяйте гипотезы на development/validation. Фиксируйте гипотезу и критерий успеха до запуска. Финальную выборку открывайте для зафиксированного кандидата; после серии подсмотров называйте её validation и найдите другую независимую проверку, если данные позволяют.

## За что стоит бороться

1. Результат отвечает точному вопросу из задания.
2. Есть честная точка сравнения и проверка, приближенная к будущему использованию.
3. Можно показать один сложный случай и объяснить решение.
4. Все числа в защите связаны с конкретным артефактом.
5. Решение запускается и сдаётся в требуемом формате.

Не начинайте UI, авторизацию, чатбота, RAG, мобильное приложение или деплой, пока не понятно, какой обязательный пункт они закрывают. Нужный для кейса интерфейс делайте после первого рабочего пути через данные.
